# 部署指南

5 步上手，本机或服务器通用。

## 前置：装 Docker Desktop

- Windows / Mac：下载 [Docker Desktop](https://www.docker.com/products/docker-desktop/) 安装即可
- Linux：按 [Docker 官方 Ubuntu 安装指南](https://docs.docker.com/engine/install/ubuntu/) 安装 Docker Engine 与 Compose 插件；其他发行版选择对应官方指南

确认装好并已启动：终端运行 `docker info` 与 `docker compose version`。只有 `docker --version` 有输出不能证明 Docker daemon 可用。

## 先选择交付物

- **源码部署**：从本公开仓库取得完整源码，可以继续开发和重建镜像；必须按本指南明确拉取基础镜像并构建应用镜像。
- **离线运行包**：收到 `ec-data-platform-YYYYMMDD.zip`，只用于运行，已包含 Docker 镜像和经脱敏、哈希锁定的前台利润模板，不含完整源码和真实业务数据。优先阅读[离线包使用说明](离线包使用说明.md)。

以下步骤以源码部署为主。

## 部署步骤

### 1. 解压 / 克隆代码

```bash
git clone https://github.com/wangge-dev/ec-data-platform-open.git ec-data-platform
cd ec-data-platform
```

GitHub 自动生成的源码 ZIP 也不是离线运行包。普通离线运行包不含完整开发历史或全部测试，不能替代源码。

### 2. 配置环境变量

```bash
cd deploy
cp .env.example .env
```

用编辑器打开 `.env`，先设置一项实例标识和四项必填密钥；需要 AI 功能时再填写 API Key：

- `INSTANCE_ID`：这套实例稳定且唯一的运维标识，例如 `customer_a_prod`；只用 3～63 位小写字母、数字、下划线或连字符，上线后不要随意改名
- `DEEPSEEK_API_KEY`：可选；需要 AI 功能时再配置
- `JWT_SECRET`：生成一段长随机字符串
  - Mac/Linux：`openssl rand -hex 32`
  - Windows PowerShell：`-join ((1..32) | %{ '{0:x}' -f (Get-Random -Max 16) })`
- `POSTGRES_PASSWORD`：自己起个强密码
- `APP_DB_PASSWORD`：应用数据库账号密码，和超级用户密码分开
- `ADMIN_PASSWORD`：`admin` 账号首次登录密码，设置一个唯一的强密码

`CORS_ORIGIN` 默认 `http://localhost:3997`，如果你部署到服务器 IP `1.2.3.4`，就改成 `http://1.2.3.4:3997`。

如需在同一台机器并行部署多套实例，**不要修改现有项目的 `.env` 或运行中的容器**。在第二套实例的 `deploy/.env` 中设置一个唯一 `COMPOSE_PROJECT_NAME`，并同时设置唯一的宿主机端口和容器名称。`COMPOSE_PROJECT_NAME` 会给 Compose 管理的卷加上独立前缀；只要以下命令始终带同一个项目名，`down -v` 只会清理这套并行实例的卷，不会命中现有项目。

```dotenv
# deploy/.env for a separate instance; choose a name not used by another project
INSTANCE_ID=customer_a_parallel
COMPOSE_PROJECT_NAME=ec-data-platform-parallel
POSTGRES_HOST_PORT=127.0.0.1:15432
REDIS_HOST_PORT=127.0.0.1:16379
API_HOST_PORT=127.0.0.1:14000
WEB_HOST_PORT=127.0.0.1:13997
POSTGRES_CONTAINER_NAME=ec-data-parallel-postgres
REDIS_CONTAINER_NAME=ec-data-parallel-redis
MIGRATE_CONTAINER_NAME=ec-data-parallel-migrate
API_CONTAINER_NAME=ec-data-parallel-api
WEB_CONTAINER_NAME=ec-data-parallel-web
CORS_ORIGIN=http://localhost:13997
```

宿主端口默认只绑定 `127.0.0.1`。只有在已经配置防火墙或反向代理并明确需要局域网访问时，才应显式改成其他监听地址；不要用裸端口无意中发布到全部网卡。

For PowerShell, set the same project name for the current shell before every parallel lifecycle command:

```powershell
$env:COMPOSE_PROJECT_NAME = "ec-data-platform-parallel"
docker compose --project-name $env:COMPOSE_PROJECT_NAME up -d
docker compose --project-name $env:COMPOSE_PROJECT_NAME ps
docker compose --project-name $env:COMPOSE_PROJECT_NAME down -v
```

For Bash, use the equivalent explicit project selection:

```bash
export COMPOSE_PROJECT_NAME=ec-data-platform-parallel
docker compose --project-name "$COMPOSE_PROJECT_NAME" up -d
docker compose --project-name "$COMPOSE_PROJECT_NAME" down -v
```

Leave `COMPOSE_PROJECT_NAME` commented in the existing single-project `.env` to preserve its current container and volume behavior. Container-internal service discovery remains `postgres`, `redis`, `api`, and `web`.

### 3. 启动所有服务

源码仓库首次启动时，在 `deploy/` 目录显式取得两个基础服务镜像，再构建 API/Web 应用镜像。Compose 同时服务源码部署和离线包，为防止离线启动意外联网，五个服务都固定为 `pull_policy: never`；所以不能把一次裸 `docker compose up -d` 当作全新电脑的镜像下载入口。

```bash
docker pull postgres:16
docker pull redis:7-alpine
docker compose build --pull api web
docker compose up -d
```

第一次会下载基础镜像并构建 api / web 镜像，通常需要 **2~5 分钟**（取决于网速）。`migrate` 复用刚构建的 `deploy-api:latest`。随后 Compose 会先运行一次性的 `migrate` 服务，再启动 API 和 Web：

```bash
docker compose ps -a
```

应当看到 `postgres`、`redis`、`api`、`web` 正常运行且 API/Web 健康检查为 `healthy`；one-shot `migrate` 容器应为 `Exited (0)`。`migrate` 会在连接数据库前执行与离线启动器一致的四密钥预检，再执行迁移；任一预检或迁移失败都会非零退出，API 不会启动。

### 4. 等 API 启动完成（10~20 秒）

启动生命周期如下：
- PostgreSQL 首次建库时创建最小权限账号 `ec_app`，密码取自 `APP_DB_PASSWORD`
- one-shot `migrate` 服务等待 PostgreSQL 健康，先验证 `POSTGRES_PASSWORD`、`APP_DB_PASSWORD`、`ADMIN_PASSWORD`、`JWT_SECRET` 的长度、字符、占位符和互异合同，再使用迁移账号执行固定表迁移和权限收敛，然后以退出码 0 结束
- `ec_app` 的 `search_path` 固定为 `public,user_data`：未限定的固定表查询优先命中 `public`；动态表建表和表模式操作仍显式限定或解析到 `user_data`
- API 仅在 `migrate` 成功后启动；seed 只在数据库中还没有 `admin` 账号时使用 `ADMIN_PASSWORD` 创建该账号，已有账号会跳过
- API 和 Web 继续运行，并由健康检查确认可用

观察迁移结果和服务日志：

```bash
docker compose ps -a migrate
docker compose logs migrate
docker compose logs -f api
```

确认 `migrate` 为 `Exited (0)`，再看到 API 启动日志即可；Ctrl+C 退出实时日志。

### 5. 打开浏览器登录

访问 **http://localhost:3997**（或 `http://服务器IP:3997`）

- 用户名：`admin`
- 密码：使用 `deploy/.env` 中设置的 `ADMIN_PASSWORD`

必须显式设置 `ADMIN_PASSWORD`，并为每套部署使用唯一强密码。它只在数据库中还没有 `admin` 账号时用于首次创建；修改 `.env` 或重启服务不会重置已有密码，恢复数据库后也应使用库中现有密码登录。需要重置时走已授权的“设置 → 用户管理”，不要把修改环境变量或运行演示 seed 当作密码重置入口。离线启动脚本不会提供或宣传默认管理员密码。

源码和离线启动都要求 `POSTGRES_PASSWORD`、`APP_DB_PASSWORD`、`ADMIN_PASSWORD`、`JWT_SECRET` 使用不带引号的 ASCII token；前三项至少 12 字符，`JWT_SECRET` 至少 32 字符，四项必须互不相同且不能保留 `change_me` 占位符。两个数据库密码会直接进入 PostgreSQL URI，只能使用字母、数字、点、下划线、波浪号和连字符。离线启动器还要求每项在 `.env` 中恰好出现一次，并在加载镜像前拒绝行尾注释、`$` 插值、空白、引号或反斜杠；源码 Compose 的迁移容器会在数据库迁移前再次执行运行时合同，避免绕过启动器后带弱密钥启动 API。

离线包中的五个服务固定使用 `pull_policy: never`。启动器会先加载并核对包内镜像，再以 `--no-build --force-recreate` 启动；不会因 `latest` 标签从网络拉取替换包内镜像。若本机 Compose 不支持该配置，启动前的 `docker compose config --quiet` 会在加载镜像前失败关闭。

登录后立刻去**设置 → 用户管理**改密码！

## 装上或重建合成驾驶舱（可选）

平台首次启动是空的。正式 API runtime 已包含受审计的一次性维护入口。在 `deploy/` 目录执行：

```bash
docker compose exec api npm run demo:rebuild
```

源码开发环境也可以在仓库根目录执行：

```bash
pnpm --filter @ec/api demo:rebuild
```

该命令生成 4,480 行确定性合成经营事实、13 个卡片（其中 12 个 ECharts 图表）和 1 个共享数据集。重建过程先导入带内部 staging 标记的新来源；新来源、数据集、图表和看板全部创建成功后，才在同一事务中切换并删除旧的已标记演示。切换失败会保留旧演示并补偿删除 staging，不会先清空旧数据。

清理当前合成驾驶舱使用：

```bash
docker compose exec api npm run demo:clear
```

删除权限只来自 `syntheticDemo=true + moduleCode=cockpit_demo` 或内部 staging 标记；文件名、数据集名或看板名本身都不授予删除权限。因此该命令不是“清空业务数据”命令，也不能用于分享前删除真实数据。

只有实例确实来自旧版 5-SKU 面霜演示时，才执行一次旧演示迁移：

```bash
docker compose exec api npm run demo:migrate-legacy
```

旧版迁移必须同时匹配旧来源名、旧文件名、旧数据集、两张旧图表以及旧看板说明；信号不完整或出现多个候选时关闭失败，不按保留文件名删除。命令会输出 JSON 审计记录，重复执行不会扩大删除范围。

## 常用运维命令

```bash
# 查看所有容器状态
docker compose ps

# 查看某个服务日志（实时）
docker compose logs -f api

# 重启某个服务
docker compose restart api

# 停止并移除容器，保留数据卷
docker compose down

# 永久删除这套实例的数据卷（只有明确要清空时才执行）
docker compose down -v

# 改了代码后重新构建
docker compose build --pull api web
docker compose up -d
```

## 常见问题

### Q1：访问 localhost:3997 拒绝连接？

容器没起来。`docker compose ps` 看哪个挂了，`docker compose logs <服务名>` 看错误。

### Q2：3997 端口被占用？

在 `.env` 设置 `WEB_HOST_PORT=8080`，同时把 `CORS_ORIGIN` 改成 `http://localhost:8080`，然后访问该地址。

### Q3：AI 出图报错 "模型调用失败"？

`.env` 里 `DEEPSEEK_API_KEY` 没填或失效。改完 `.env` 后跑 `docker compose up -d` 重启。

### Q4：怎么备份数据？

不要再用 shell 重定向的裸 SQL 作为正式备份。先在仓库或离线包之外创建一个受控、加密的备份目录，再从项目根目录执行：

```powershell
# Windows / source tree
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/instance-backup.ps1 -OutputRoot "D:\encrypted-backups"
```

```bash
# macOS/Linux / source tree
bash scripts/instance-backup.sh --output-root /secure/encrypted-backups
```

离线运行包使用根目录下名称更短的 `backup.ps1` 或 `backup.sh`。脚本会生成 PostgreSQL 自定义格式转储和 `instance-backup/v1` 哈希清单，且拒绝把备份写进源码树或离线包。该目录含真实业务数据、账号密码哈希和可能存在的加密连接凭据，必须按敏感资产加密、限权并异机保存。

恢复会完整替换目标数据库并清空 Redis 临时状态，因此必须同时确认目标 `INSTANCE_ID` 和覆盖动作：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/instance-restore.ps1 `
  -BackupPath "D:\encrypted-backups\ec-data-instance-backup-customer_a_prod-20260818T020000Z" `
  -ConfirmInstanceId customer_a_prod `
  -AcknowledgeDataOverwrite
```

```bash
bash scripts/instance-restore.sh \
  --backup-path /secure/encrypted-backups/ec-data-instance-backup-customer_a_prod-20260818T020000Z \
  --confirm-instance-id customer_a_prod \
  --acknowledge-data-overwrite
```

不同代码修订还必须显式确认版本兼容风险；具体参数、失败关闭行为、`ENCRYPTION_KEY` 保留要求和离线包命令见[离线包使用说明](离线包使用说明.md)。脚本不等于完整备份制度：生产环境仍需配置定时调度、保留策略、异机副本、失败告警和真实恢复演练。

### Q5：多用户怎么管理？

登录后 → 设置 → 用户管理。**（V0.27 起 RBAC）新建/改/删用户，外部 SQL 的测试、保存、删除、列表、表枚举和查询，以及数据源配置的新增、修改和删除，全部限管理员（admin）**。文件删除、批量删除、同名文件覆盖，以及品牌字典、成本字典、店铺 PIC 字典等维护文件的上传也仅限管理员。普通用户仍可上传新的经营 Excel/CSV，使用已授权的普通数据模块并创建自己的业务模块，但不能进入全局运维入口。仍是内部小团队设计，**不要开管理员账号给不可信成员**。

> 安全提醒：应用默认使用最小权限角色 `ec_app`；Postgres 超级用户 `ec` 只用于初始化和维护。外部 SQL 必须使用目标数据库自身的最小权限只读账号；应用层的只读事务和 SQL 校验不能替代数据库授权。外部 SQL 连接默认拦截内网/元数据地址（SSRF 防护），如需连内网 DB 才显式设 `ALLOW_PRIVATE_SQL_HOST=1`。启用 TLS 时必须填写与服务端证书匹配的 DNS 域名，不能填写纯 IP；证书校验失败会拒绝连接，不会降级。

## 升级

代码更新后：

```bash
git pull
cd deploy
docker compose build --pull api web
docker compose up -d
```

每次 `docker compose up -d` 都会先运行 one-shot `migrate` 服务。只有迁移成功并以 0 退出后，API 才会启动；迁移失败时先查看 `docker compose logs migrate`，修复后重新运行 Compose。不要用 API entrypoint 或应用账号手工接管固定表迁移和所有权。

升级到包含会话版本校验的版本后，升级前签发的登录 Token 会按安全策略失效，所有用户需要重新登录；管理员重置某个用户密码后，该用户此前的 Token 也会立即失效。

## 离线发布包

离线发布包会同时复制 `apps/api/extensions/`，与 Compose 中的只读挂载保持一致，避免宿主空目录遮住镜像内扩展。目录只允许放经过验证的配置资产及随附说明文档；模块、连接器和垂直方案的机器清单必须分别符合 `module-manifest/v1`、`connector-manifest/v1` 和 `vertical-solution/v1`。禁止可执行脚本、连接密码和业务数据进入该目录或交付包。

PowerShell 和 Bash 默认都输出到**当前仓库**的 `release/`，不依赖电脑盘符或固定项目路径。可以显式指定其他安全目录。

Windows PowerShell 打包命令：

```powershell
pwsh -NoProfile -File scripts/package-release.ps1
```

规范输出：

```text
Release ZIP: <当前仓库>\release\ec-data-platform-YYYYMMDD.zip
Bytes: <archive-bytes>
SHA-256: <64-hex-digest>
```

Windows PowerShell 验收命令：

```powershell
pwsh -NoProfile -File scripts/verify-release.ps1 `
  -ArchivePath "release\ec-data-platform-YYYYMMDD.zip" `
  -WorkingRoot "C:\ec-data-release-verification"
```

规范成功输出：

```text
Verified ec_app role, API health, Web HTTP 200, admin login, <N> baseline modules, front-profit user-module creation, rendered chart(s), dashboard, and backup/restore recovery.
```

验证器使用独立的 Compose 项目、端口、容器名和卷；其中包括唯一的 `INSTANCE_ID` 与 `MIGRATE_CONTAINER_NAME`。它会在空库完成登录、模板上传、DIY 模块、默认图表渲染、看板创建、实例备份、备份后变更和完整恢复复核，并在结束时清理该验收项目。`WorkingRoot` 必须是明确指定的专用非根目录。

Git Bash 可选输出路径：

```bash
export RELEASE_ROOT="/path/to/output"
bash scripts/package-release.sh
```
