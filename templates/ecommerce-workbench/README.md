# 电商经营工作台 v1

本方案是公开仓库的可修改配置与合成样例，项目自有部分按 GPL-3.0-only 分发；独立工作台 ZIP 附带 `LICENSE` 与 `THIRD_PARTY_NOTICES.md`，源码仓库根目录也有同名文件。它不包含任何真实经营报表或可共享的用户数据库。

这是一个可导入现有数据平台的纯配置方案：接收七张已经整理好的淘系、拼多多标准表，并把七个底层模块收拢为四个业务入口。它不包含原始导出转换器、数据库、账号、密码、API Key 或真实经营数据，也不是多租户 SaaS。

## 安装后有什么

| 业务入口 | 底层标准表 | 可用核心指标 |
|---|---|---|
| 淘系经营概览 | `taobao_trade_day` | 支付金额、访客、买家、转化率、客单价 |
| 淘系交易结构 | `taobao_terminal_day`、`taobao_price_band_day`、`taobao_category_month` | 终端、价格带、叶子类目结构 |
| 拼多多推广 | `pdd_ads_account_day`、`pdd_ads_product_period` | 花费、交易额、投产、曝光与点击 |
| 拼多多订单与数据质量 | `pdd_order_item` | 有效销售、订单状态、售后、成交时间完整性、推广商品覆盖 |

四个入口来自模块分类，不是把七张表强行 JOIN 成一张大宽表。这样能保留各平台原始粒度，也更容易单独替换某一类数据。

七个模块首次成功处理数据后，每个模块会自动生成“第一项指标”的趋势和排行，共 14 张基础图表。`solution/*blueprint.json` 列出的多指标推荐图表只是搭建参考，当前不会随方案自动导入；访客、转化率、ROAS、CTR、售后和质量等图表需要在分析中心按蓝图手动创建。

## 五步安装

1. 在一个空白或已备份的本地实例中，以管理员登录。
2. 打开侧边栏“方案交付”，选择 `solution/ecommerce-operations-workbench.solution.json`。
3. 依次点击“校验方案包”和“应用方案”。系统会原子安装七个模块，不会携带业务数据。
4. 到“数据”页上传 `samples` 下的七个 Excel，并按同名模块分配、运行 ETL。样例只用于验证流程。
5. 打开“经营驾驶舱”，应看到四个入口。确认后，在接入真实文件前先移除或取消分配样例数据源，避免样例与真实数据相加。

每个样例都只有一个 `standard_table` 工作表，日期固定在 2099 年，账户、商品、类目和状态均带“示例”标记，批次固定为 `SAMPLE_BATCH_20991231`。

版本要求：2026-09-02 及更早的离线运行包不包含本方案依赖的四入口和图表修复，不能与本配置 ZIP 直接配套分享。应使用包含当前工作台改造的平台版本；若只有旧离线包，先不要导入本方案。

如果目标实例已经装过本方案的早期测试版，方案更新不会自动重建曾经生成的默认图。请在备份后使用空白实例重装，或手工重建“拼多多推广商品周期”的排行图并同时加入 `period_start`，避免旧图继续因缺少报告期而失败。

## 换成自己的数据

- 保留表头，不需要的值留空，不要用 0 代替未知值。
- 订单号、商品 ID、SKU ID 和类目 ID 按文本保存，避免长数字被 Excel 改写。
- 比率写小数：10% 写 `0.1`；金额和数量写数值，不要混入“元”“件”等文字。
- `source_account_alias` 使用稳定别名；`source_batch` 每次导入使用可追溯且不敏感的批次名。
- 拼多多订单的成交指标使用 `effective_*` 字段；取消或退款成功记录仍保留，但不计入有效销售。
- `order_weight` 每个订单只在一行写 1；多商品订单其余行写 0，防止把商品行数误当订单数。
- 类目表同时保留一级与叶子类目，默认语义口径只计算 `category_level=leaf`，防止上下层金额重复汇总。
- 商品推广周期表属于快照。同一报告期内可按商品汇总，不要把重叠报告期直接相加。
- 访客、买家和支付商品数属于去重口径，不要跨日期直接相加；终端、价格带和类目之间也可能重复，只适合在同一粒度下比较。

如果拿到的是原平台导出而不是标准表，本配置 ZIP 不能直接转换。当前源码版另有两套只读转换器：`sycm-standardize.mjs` 将多工作簿拆成淘系四表，并在写出前拦截必要字段空值和对账不平；`pdd-standardize.mjs` 选择完整账户日表、订单明细和一个明确报告期的商品快照，并跳过重复子区间。转换后的文件名会与七个模块自动识别规则一致；结果应写到源目录之外，再上传平台。处理其他月份时，要显式传入 `--ads-account-period YYYY-MM-DD:YYYY-MM-DD` 和 `--ads-product-period YYYY-MM-DD:YYYY-MM-DD`，不要沿用验收数据的默认期间。

多张转换结果不是一次整组原子替换。每个批次应写入新的空目录；只有命令完整成功且对账通过后，才把这一批文件上传平台。中途失败时丢弃该输出目录并重跑，不要把新旧目录中的表混用。

## 更新与恢复

更新时用新文件名上传并运行 ETL；成功后核对行数、日期范围和图表，再删除旧数据源。新文件处理失败时，模块会保留上一版结果，删除失败文件即可恢复。

上传、处理和删除旧源不是一次原子切换：核对期间看板会短暂包含新旧两批数据。因此应在维护窗口更新，不要在切换过程中读取经营结论。方案配置可以升级和回滚，但回滚方案不会替代数据备份。

## 能 DIY 到哪里

可以直接做：增删字段、改字段别名、增加同表指标和维度、调整图表、替换样例、按模块独立更新与恢复。

需要技术人员先整理：复杂多表 JOIN、任意多层表头、跨表业务公式、重叠快照去重、特殊清洗和完全自由的数据建模。这些不是靠一个模板就能安全自动推断的；更稳妥的做法是先产出一张口径明确的标准表，再交给模块和驾驶舱。

## 包内边界

- `solution/*.solution.json`：可由“方案交付”页面校验、安装、升级和回滚的正式配置。
- `solution/*blueprint.json`：四入口及推荐图表的可读搭建说明，系统当前不会自动导入。
- `samples/*.xlsx`：固定合成数据，只用于安装验证和字段参考。
- `solution/package-manifest.json`：包内容与隐私声明。

不要用正在运行的在线实例备份来制作分享包；数据库卷、上传历史、处理结果、图表和看板都可能包含真实信息。
